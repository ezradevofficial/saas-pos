# Project brief

The product name has not been chosen. Never write a product name in code, UI text, package names, folders, database names, emails, tests or docs. Read the display name from one setting (`APP_NAME` in the environment and the `app.name` translation key) and use neutral identifiers everywhere else (`app`, `platform`, `ds`).

This is a multi-tenant SaaS business platform for Kenya and the DR Congo: a point of sale at its core, plus inventory, stores, procurement, accounting, HR, payroll, CRM, e-commerce, fixed assets and manufacturing. Every module can be sold and used on its own. Customers self-onboard, pick modules and pay monthly or yearly.

This file tells you how to work in this repository. Read it fully before every task.

## Stack

- **Backend:** Laravel (latest stable), PHP 8.3+, PostgreSQL 16+, Redis, Laravel Horizon for queues.
- **Web app (back office, admin, builders):** React with JavaScript (no TypeScript), Vite, Tailwind CSS and shadcn/ui (set up with `"tsx": false` in `components.json`, so components are generated as `.jsx`).
- **POS and mobile apps:** React Native with JavaScript (Expo with a development build), NativeWind for styling with Tailwind classes, SQLite on the device via WatermelonDB for offline data.
- **Hosting:** Linode (Akamai Cloud): separate servers for web/API, queue workers and the database (or Managed PostgreSQL), a NodeBalancer, and Object Storage for files.
- **Languages:** English and French only.

Do not add another language, framework or database without asking.

## Architecture rules

1. **Modular monolith.** Each module owns its tables, routes and UI. Modules never read or write another module's tables. They communicate through domain events (`SaleCompleted`, `GoodsReceived`, `PayrollApproved` and so on) and a small set of core services.
2. **Stand-alone modules.** A module must work with only the core installed. Integrations with other modules switch on only when both are subscribed. Example: POS posts journals only if Accounting is active.
3. **Feature flags per tenant.** Routes, menus, permissions and event listeners of a module load only when the tenant subscribes to it (RBAC-08).
4. **Configuration over code.** Never add per-customer code branches. Customer differences live in data: workflows, custom fields, templates, themes, country packs.
5. **Country packs are data.** Tax rates, payroll bands and statutory rules are effective-dated rows, never constants in code (CP-01, CP-02).

## Multi-tenancy (TEN-01)

- Every tenant table has `tenant_id` (UUID), indexed and not null.
- PostgreSQL row-level security enforces isolation. The app sets `app.tenant_id` on each connection after authentication. Never bypass this, including in jobs, commands and reports.
- Hierarchy: tenant (group) → companies → branches → locations → devices (TEN-02 to TEN-05).
- Every new table needs a tenant-isolation test before the PR is merged.

## Data conventions

- Primary keys: UUID v7. Offline POS records get their UUID on the device.
- **Money:** store as `bigint` in minor units plus a `currency` (ISO 4217) column. CDF has 0 decimals; KES and USD have 2. Never use floats for money.
- **Exchange rates:** `numeric(18,8)`. Every multi-currency document stores the rate used and the base-currency amounts (CUR-04).
- **Timestamps:** UTC in the database; convert using the company or branch time zone.
- **Never hard-delete business records.** Archive them (TEN-06). Audit every create, update, archive, approval, void, refund, discount and price override (AUD-01, AUD-02).
- Custom field values live in a `jsonb` column with GIN indexes where filtered (CF-06).

## Security and access

- Every endpoint checks permissions through Laravel policies, scoped by company, branch and location (RBAC-01 to RBAC-09). The UI hides what the user can't do, but the API is the only real guard.
- Permission names follow `module.resource.action`, e.g. `pos.sale.void`.
- **Roles and permissions use spatie/laravel-permission, extended:**
  - Spatie provides the permission catalogue, roles, role-permission links and the Gate/policy integration (`can()`, `@can`, middleware).
  - The permission catalogue is global; each module registers its own permissions. Roles belong to a tenant: add `tenant_id` to Spatie's `roles` table under the same row-level security as every other tenant table. System role templates (RBAC-03) are seeded per tenant and can be copied but not edited.
  - Do **not** use Spatie's direct `model_has_roles` assignments or its "teams" feature for scope. Use our own `role_assignments` table (`tenant_id`, `user_id`, `role_id`, `scope_type` = company | branch | location, `scope_id`) and a `ScopeResolver` service that answers "can this user do X at this location?", including inheritance (a branch role covers that branch's locations; a company role covers its branches) (RBAC-04).
  - Field rules (RBAC-05) and limit rules (RBAC-06: max discount, refund, approval amount) are our own small services, read by policies, API resources (to hide fields) and the UI.
  - Spatie's permission cache must be keyed by tenant (and flushed per tenant on change) so one tenant's roles can never be served to another.
  - Every role, permission and assignment change is audited (RBAC-12). The last active Owner cannot be removed or demoted (RBAC-10).
  - Tests: a user with a role at Branch A is refused at Branch B; a company-scoped role reaches every branch; cached permissions never cross tenants.
- Validate every request with Form Requests. Never trust IDs from the client without checking they belong to the tenant and the user's scope.
- Secrets live in environment variables, never in the repo.

## Offline POS sync (NFR-04)

- The POS must sell for at least 7 days with no connection.
- Sales are append-only and synced idempotently: the server ignores a sale whose UUID it already has.
- Master data (items, prices, customers, promotions, rates, taxes) syncs down in increments using `updated_at` cursors.
- Conflict rules: the server wins for prices and master data; the device wins for completed sales.
- Receipt numbers come from number ranges pre-allocated to each device (NUM-02).
- Fiscal submissions (KRA eTIMS, DRC DGI) queue on the server and retry until accepted.

## Front-end rules

- All colours, fonts, spacing, radii and shadows come from tokens. No hard-coded values in components (BR-01). Tenant themes override tokens at runtime.
- **Tailwind and shadcn/ui (web):**
  - The tokens package generates the CSS variables and a Tailwind preset. Tailwind's theme reads only those variables, so classes look like `bg-surface-200 text-ink border-border rounded-md`. Never use Tailwind's default palette (`bg-blue-500`, `text-gray-700`) or arbitrary values (`bg-[#0b5d6e]`, `p-[13px]`).
  - Map shadcn's variables to ours in `web/src/index.css` so shadcn primitives take the design-system look: `--background` → `surface-100`, `--card` and `--popover` → `surface-200`, `--muted` → `surface-300`, `--foreground` → `ink`, `--muted-foreground` → `ink-muted`, `--primary` / `--primary-foreground` → `primary` / `on-primary`, `--accent` → `surface-300` (shadcn's "accent" is a hover tint; our `accent` token is the near-black decisive action, used only by the `pay` button variant), `--destructive` → `danger`, `--border` and `--input` → `border-strong`, `--ring` → `focus`, `--radius` → `radius-md`. Dark mode uses the `.dark` class with the dark token values.
  - Add shadcn components with the CLI, never by hand-copying. Keep generated files close to stock; put our own behaviour in `components/ds/` wrappers so shadcn updates stay easy.
  - Use `cn()` (clsx + tailwind-merge) for conditional classes. No inline `style` except for values set at runtime from tenant themes.
- **NativeWind (POS and mobile):**
  - Style React Native components with NativeWind classes that use the same token names as the web (`bg-surface-200 text-ink rounded-md`). Same ban: no Tailwind default colours, no arbitrary values, no `StyleSheet` colours or sizes typed by hand.
  - Tenant themes and dark mode switch at runtime through NativeWind's CSS-variable support (`vars()` on the root view), fed by the tokens package, so a white-label theme changes the POS without a new app build.
  - shadcn/ui is web-only. Build the mobile versions of the 18 design-system components in `pos/src/components/ds` with NativeWind, matching the web versions' props and behaviour.
  - NativeWind supports a specific Tailwind major version. Check it before setup; if it differs from the web's Tailwind version, the tokens package generates a preset for each so both apps still share one token source. Record the decision in `docs/adr/005-styling.md`.
  - Keep heavy lists (product grid, cart, tables) fast on low-end Android: use `FlatList`/`FlashList` and avoid recomputing class strings on every render.
- Build the 18 design-system components (Button, TextField, Select, Checkbox, Switch, StatusBadge, Alert, SyncStatus, Money, KpiTile, DataTable, Card, Tabs, Dialog, PosTile, SaleTotal, StageTracker, ApprovalCard) once in each app and reuse them. Follow each component's guidelines in the design system.
- **Look and feel: quiet and premium.** Near-white surfaces, graphite type, hairline borders instead of shadows, a deep muted teal (`primary`) used sparingly, and near-black (`accent`) only for the one decisive action per screen (Charge, Approve all, Complete). Status is a small dot plus a word, never a bright filled pill. Weights 400 and 500, 600 only for page and dialog titles, never 700. Corners 6px for controls, 10px for cards. Follow the design system's README exactly; if a screen starts to look busy or playful, remove colour before adding anything.
- Fonts: Geist for everything, with tabular figures for money and quantities; Geist Mono only for codes in technical views.
- **Customisation is a core feature (BR-01 to BR-08, LAY-01 to LAY-08, TPL-01 to TPL-05):**
  - Themes are sets of token values. Ship four: Light (default), Dark, and the presets Executive and Warm from `design/tokens.json`. A tenant theme = a preset plus overrides, stored as JSON and applied at runtime as CSS variables (web) and NativeWind `vars()` (POS).
  - Tenants may override only: logo, `primary` and its pair (`primary-hover`, `on-primary`, `primary-tint`), `accent` and its pair, sidebar light or dark (the `sidebar-*` tokens), corner style (sharp, standard, soft), and font from a curated list (Geist, IBM Plex Sans, Newsreader + Geist). Status colours, spacing, type sizes and the focus ring are never overridable.
  - The theme editor derives hover and tint values and refuses to save any pair under WCAG AA contrast (BR-03).
  - Layouts (dashboards, navigation per role, forms, list views, the POS screen) and document templates are versioned JSON configuration rendered by the same components. Never build per-tenant screens or CSS.
  - Printed documents are black on white in every theme; fiscal elements (KRA eTIMS, DRC DGI, tax lines, QR codes) are locked in templates.
- POS touch targets are at least 48px.
- Text meets WCAG AA contrast in light and dark themes.

## Writing in the UI

- Every user-facing string goes through translation files (`en`, `fr`). A missing translation fails the build (L10N-02).
- Sentence case. Buttons are verbs naming the result ("Approve", "Charge USD 48.50"); never "OK" or "Submit".
- Money always shows its currency code first: "KES 12,450.00", "CDF 135,000".
- Errors say what happened and what to do next. No emoji, no exclamation marks.

## Testing and quality

- Backend: Pest (or PHPUnit) feature tests for every endpoint, including permission-denied and other-tenant cases.
- Web: Vitest and React Testing Library. POS: Jest, plus sync tests that simulate going offline, duplicate uploads and conflicts.
- CI runs lint, tests and the tenant-isolation suite on every PR. A PR doesn't merge if any fail.
- Run the relevant tests yourself before saying a task is done, and report the results.

## Git workflow

- Branches: `feat/<area>-<short-name>`, `fix/...`, `chore/...`.
- Small PRs, one concern each. The PR description lists the requirement IDs covered and how they were tested.
- Never commit directly to `main`.

## Sprint 1: foundation

Goal: a running skeleton where a tenant can sign up, sign in, create companies, branches and users, and see only what their role allows.

1. **Scaffold the repo** using the layout above: Laravel API, React web app, React Native POS app (Expo), shared tokens package. Docker Compose for local PostgreSQL and Redis.
2. **Tokens package and styling:** compile `design/tokens.json` to CSS variables (light and dark), a Tailwind preset for the web and a NativeWind preset plus runtime variables for the POS.
