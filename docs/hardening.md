# Hardening and observability (NFR-01 to NFR-11)

Phase 8, stage 8C. Each non-functional requirement in `docs/platform-core-spec.md` is met by an **automated check** (a test, a CI job or a build gate that fails on its own) where that is feasible, and by a **runbook** (a documented procedure a person runs on a schedule) where it is not. Many have both. This file is the matrix; the details live in the linked documents.

Status: **Done** means built and tested in this repository. **Owner** means the code and documents are ready and a value only the owner can provide (credentials, a choice of supplier) is still missing.

## Status page (NFR-01)

Options, in order of preference:

1. **A hosted status page with its own uptime checks** (for example Better Stack, Instatus or UptimeRobot's status pages). It runs outside Linode, so it stays up when we are down, and it can post incidents. It probes `GET /up` and `GET /api/health/ready` every minute from several regions. Cost: a monthly fee. Recommended.
2. **A static page on Object Storage**, fed by `status.json`. `php artisan health:status` (scheduled every minute) writes the readiness result, component states only, to `STATUS_DISK` (`STATUS_PATH`); point it at a public-read bucket. A tiny static page on a separate bucket reads it. No dependency and no fee, but it shares Linode's fate and cannot report its own outage, so an external uptime probe is still needed for alerts.
3. **GitHub Pages with a scheduled workflow** probing the API. Free and off-platform, but a 5-minute minimum schedule and no incident tooling.

The owner chooses. Until then `status.json` exists and the uptime alert in [observability.md](observability.md#alert-rules) is the source of truth.
