# Phase 3 report: workflow engine, approvals, automation, notifications

Date: 2026-10-08. Plans: `docs/superpowers/plans/2026-10-08-lists-and-pickers.md` (done first, owner request) and `docs/superpowers/plans/2026-10-08-phase-3-workflow-approvals-automation.md`. ADRs: `docs/adr/002-tenancy-rls.md` (scheduler tenant functions), `008-lists-and-pickers.md`, `009-notifications.md`.

## Outcome

All Phase 3 tasks are on main, plus the lists-and-pickers work the owner asked for before it and a filter drawer the owner asked for during it.

- **Notifications** (NOT-01..06): one service for every module; in-app inbox and bell, email; push/SMS/WhatsApp adapters with fake drivers; tenant templates (one text per event and channel); preferences with mandatory channels; daily/weekly digests; delivery log with retries. Invitations and new-device alerts go through it; one-time codes stay outside by design (ADR 009).
- **Workflow engine** (WF-01..11): document type registry, versioned flows (draft, publish, roll back, discard draft, copy, restore default), stages, entry/exit rules, branching, parallel split/join, create-next-document, stage roles, business-hour due times with reminders, overdue notices and escalation, return and cancel, history, status page with actions, stage volume and bottleneck dashboard. Visual builder on React Flow (desktop and tablet; read-only on phones).
- **Approvals** (APR-01..09): single, any/all/majority, sequential chains; approver types (named user, role in scope, branch manager, department head, cost-centre owner, manager N levels up); approve, reject, return, comment, attachments, request information; one inbox with "why this route" and bulk approve; reminders, escalation and final auto-decision in business time; delegation and reassignment; no self-approval with a four-eyes rule; approve by email with single-use links; version pinning.
- **Automation** (AUTO-01..07): rules with record, field, stage, date, threshold and schedule triggers; conditions; update field, change stage, assign, notify, create document, credit hold and webhook actions; test mode; run log with retries and alerts; loop protection and throttling; templates. Webhooks are signed, sent from an outbox after commit, and guarded against private addresses.
- **First real document type**: credit limit changes for customers, approved by an Accountant (tenant-level for shared customers), applied after approval with conflict detection, and shown in the customer's history.
- **Lists and pickers**: every table has search, filters in a right-side drawer with chips, sorting, a record count, rows per page, paging, column choice and CSV/Excel/PDF export (scope and field rules apply; audited; rate-limited; PDF up to 500 rows). Every dropdown is a searchable combobox.

Exit criterion checked end to end in the browser: Amina requested a credit limit change; Baraka (Accountant) got the bell notification and the inbox item, approved it; the limit was applied and shows in the customer history; an automation rule on the same flow notified the Owner; the run log, the document status page and the dashboard show it; a cancelled request settles as cancelled.

## Reviews

Risky tasks (exports, notifications, workflow engine, approvals, automation, credit limits) each had an independent review and a fix round; screens had browser checks. A whole-phase review then found three release blockers, all fixed before closing:

1. A rejected approval could end a flow as approved (parallel joins ignored outcomes; the credit type's guard was too loose).
2. An approval without a rejected path could not be rejected, and a timeout auto-reject left it pending.
3. Blocked-move messages showed hidden field values, including through the email approval endpoint.

And medium items: public holidays never loaded on deploy; scheduler commands used the owner (BYPASSRLS) connection (now SECURITY DEFINER tenant functions, ADR 002); queues and Horizon; stage reminders not acted on; duplicate documents on return; synchronous listeners that could leave a credit change pending (now queued, plus a reconcile pass); automation audit without the rule; field rules in "why this route" and automation notices; time zones on several screens; the builder's chain and reminder editors.

## CI

Main was red from the first list-export merge until near the end of the phase: only touched tests ran locally, and the CI result was not checked after merges. The failures were test faults, not app bugs (a queue worker hitting its memory limit late in the suite, a race between two token build tests, a toast raised twice under load, a test matching a new sidebar request, a fixture missing a new capability, an isolation test missing a new id field). All are fixed and main is green. The controller now checks CI after each merge. Deploy was skipped while main was red, so dev/staging received Phase 3 only at the end.

## Decisions made by the controller (say if you want otherwise)

- Exports need only the list's view permission; PDF cap 500 rows; DejaVu Sans in PDFs.
- Approvals in parallel branches are refused for now.
- Rejecting always needs a reason; "manager N levels up" means holders of a role with `core.approval.reassign` at that level.
- Credit limits: no limit = unlimited; lowering or setting a first limit is direct; raising, removing or changing currency needs a request; approval needs `core.credit_limit.approve`.
- Automation runs as the rule's last editor and switches itself off if that person can't act any more; webhook secrets are generated and shown once.
- Personal column choices stay in the browser until phase 5.
